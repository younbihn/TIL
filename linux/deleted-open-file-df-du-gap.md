# 지운 파일이 공간을 안 돌려줄 때: df 와 du 가 어긋나는 이유 (lab02, 루프 장치 32M)

## 측정 조건
- 일시: 2026-11-14 15:10 KST 무렵, lab02, 위 inode 실험과 같은 `/mnt/lab`(ext4 32M 이미지), 한 번 실행
- 절차: `dd if=/dev/zero of=big bs=1M count=20` (20 MiB 파일) → 파이썬을 백그라운드로 띄워 `open('big','rb')` 로 연 채 `os.remove('big')` 후 30초 대기 → 1초 뒤 `df -h .`, `du -sh .`, `ls -l /proc/$!/fd | grep deleted`
- 프로세스 번호: 14789 (`[1] 14789`)

## 결과
| 시점 | `df -h .` 사용 / 가용 / 사용률 | 비고 |
|---|---|---|
| `dd` 직후 | 21M / 5.0M / 81% | |
| 파일 삭제 후 1초(프로세스가 열고 있음) | 21M / 5.0M / 81% | **삭제했는데 그대로** |
| 프로세스 종료 후(`완료` 표시 뒤) | 18K / 25M / 1% | 공간 반환 |

- 같은 시점 `du -sh .`: `17K .` (`./lost+found` 는 `허가 거부`로 읽지 못함)
- `/proc/14789/fd` 에서: `lr-x------. 1 minkyluv minkyluv 64 11월 14 15:10 3 -> /mnt/lab/big (deleted)`

## 읽은 것
- `rm` 은 디렉터리에서 이름(링크)만 지운다. 파일의 데이터 블록은 열고 있는 프로세스가 하나라도 있으면 그대로 남고, 마지막 프로세스가 닫을 때 비로소 반환된다. 그래서 `df`(파일시스템이 센 사용량) 21M 와 `du`(디렉터리 트리를 걸으며 센 사용량) 17K 가 어긋났다. 차이 약 21M 가 지워졌지만 열려 있는 `big` 이다
- **`df` 는 큰데 `du` 로는 안 보일 때** 삭제된 채 열려 있는 파일을 의심한다. 찾는 명령: `ls -l /proc/<PID>/fd | grep deleted`, 시스템 전체는 `sudo lsof +L1`(이번에 실행하지 않음, 미확인)
- 해결은 그 프로세스를 재시작하거나 종료하는 것이다. 로그 파일을 `rm` 으로 지웠는데 디스크가 안 줄어드는 운영 사고의 전형이며, 로그를 지울 때는 `: > 파일`(내용만 비움)이나 `logrotate` 를 쓰는 이유다(알려진 대응이며 이번에 시험하지 않음)
