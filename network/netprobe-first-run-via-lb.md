# netprobe.py 첫 실행: 맥에서 lb01 경유 단계별 시간 (5회)

## 측정 조건
- 일시: 2026-11-14 14:05 KST 무렵, 한 번 실행(반복 안 함)
- 위치와 경로: 맥 → lb01(192.168.64.7, HAProxy 2.8.14, roundrobin) → lab01 또는 lab02, HTTP, 경로 `/health`
- 명령: `python3 scripts/netprobe.py http://192.168.64.7/health -n 5` (맥, 저장소 루트)
- 도구: `scripts/netprobe.py` (표준 라이브러리만 사용, 단계별 시간을 `time.perf_counter()` 로 측정). 맥의 파이썬 버전은 기록하지 않음(미확인)
- 같은 호스트 안의 가상 네트워크(맥과 UTM VM)라 실제 망 지연은 거의 없다. 평상시 상태(장애 주입 없음)

## 읽은 것
- **roundrobin 이 보인다**: 응답 서버가 lab02, lab01, lab02, lab01, lab02 로 번갈아 나왔다. netprobe 는 요청마다 새 연결을 만들기 때문에 연결마다 다음 서버로 배정된 것으로 보인다(5회뿐이라 분포를 단정하지는 않음)
- **dns 단계가 거의 0**: 주소를 이름이 아니라 IP로 줘서 `getaddrinfo` 가 DNS 조회 없이 끝난다. 이름으로 접속하면 이 값이 커진다(DNS 조회 시간)
- **tcp 단계 0.61 ms**: 3-way handshake 가 끝날 때까지의 시간이고 맥과 lb01 사이 왕복 하나에 해당한다. 같은 호스트 안이라 매우 작다
- **첫바이트 2.54 ms**: 요청이 lb01 에 닿고, HAProxy 가 백엔드에 다시 접속해 응답을 받아 첫 바이트를 돌려줄 때까지다. 직접 접속한 값이 없어서 이 중 HAProxy 가 더한 몫은 아직 모른다
- **첫 시도가 가장 느리다**: 12.64 ms 로 다른 4회(2.4~4.0 ms)의 3배 이상이다. 첫 시도의 dns 도 2.70 ms 로 높다. 원인은 확인하지 않음(미확인). 중앙값을 대표값으로 쓰는 이유가 이 값에서 보인다

## 한계와 미확인
- 5회 한 번뿐이라 통계적으로 약하다. 같은 호스트 안의 가상 네트워크라 실제 데이터센터 값이 아니다
- 직접 접속(맥 → lab01)과 LB 경유의 비교는 아직 안 했다. LB 가 더하는 지연은 비교 측정(각 20회) 뒤에 말할 수 있다
- 첫 시도가 느린 원인, HTTPS 단계(`tls`)는 이번 실행에 해당 없음(0.00)
- `failover_probe.py` 의 응답 시간 중앙값(5~7 ms)과는 도구와 요청 방식이 달라 직접 비교하지 않는다
