# 로드밸런서 경유 지연: 맥에서 lab01 직접 접속과 lb01 경유 비교 (각 20회)

## 측정 조건
- 일시: 2026-11-14 14:06 KST 무렵, 각 한 번 실행(반복 안 함). 직접 접속을 먼저, 이어서 LB 경유 순서로 실행
- 위치와 경로: 맥에서 시작, HTTP `/health`, 평상시 상태(장애 주입 없음)
  - 직접: 맥 → lab01(192.168.64.2)
  - LB 경유: 맥 → lb01(192.168.64.7, HAProxy 2.8.14, roundrobin) → lab01 또는 lab02
- 도구와 명령: `scripts/netprobe.py`, `-n 20`, 맥 저장소 루트에서 실행. 단계별 시간은 `time.perf_counter()` 로 측정, 요청마다 새 연결
- 맥과 VM(UTM 공유 네트워크)이 같은 호스트 안이라 실제 망 지연은 거의 없다. 맥의 파이썬 버전은 기록하지 않음(미확인)

|---|---|---|---|---|

- 보조 통계(직접 / LB 경유): 전체 최솟값 1.07 / 1.27, 최댓값 7.23 / 10.41, 평균 1.67 / 2.50. 첫 시도를 빼고 다시 계산한 중앙값 차이는 전체 +0.53, 첫바이트 +0.65, tcp −0.17
- LB 경유의 응답 서버: lab01 10회, lab02 10회로 정확히 번갈아 나옴(1번 lab01, 2번 lab02, …)
- LB 경유를 서버별로 나누면 전체 중앙값이 lab01 1.75 ms(10회), lab02 1.89 ms(10회)

## 읽은 것
- LB 를 거치면 전체 중앙값이 0.55 ms 길다. 늘어난 부분은 거의 전부 **첫바이트**(+0.69)다. 요청을 HAProxy 가 읽고 백엔드에 다시 접속해 응답을 받아 돌려주는 시간이 들어가기 때문으로 보인다(HAProxy 내부 처리 시간을 따로 재지는 않았다)
- **tcp 는 오히려 LB 경유가 0.15 ms 짧다.** 맥과 lb01 사이가 맥과 lab01 사이보다 빠를 이유를 확인하지 못했다. 표본 20회, 각 한 번 측정이고 직접 접속을 먼저 돌렸으므로 순서와 잡음의 영향일 수 있다(미확인). 그래서 이 차이는 의미 있는 차이로 쓰지 않는다
- **첫 시도가 느리다**: 직접 7.23 ms, LB 경유 10.41 ms. 이 때문에 평균은 중앙값보다 크다(직접 1.67 대 1.28, LB 경유 2.50 대 1.83). 중앙값을 대표값으로 쓰는 이유가 이 값에서 보인다
- **LB 경유의 초반 요청이 점점 빨라졌다**: 2번에서 9번까지 전체가 3.89 → 3.44 → 3.15 → 3.03 → 3.02 → 2.35 → 2.08 → 1.68 ms. 원인은 확인하지 않았다(미확인). 준비 운동 효과로 추정하나 근거는 없다
- 두 백엔드 사이의 차이(lab01 1.75, lab02 1.89 ms)는 10회씩이라 구분하지 않는다

## 이 숫자로 말할 수 있는 것과 없는 것
- 말할 수 있는 것: 이 가상 환경, 평상시, 요청마다 새 연결, `/health` 기준으로 LB 경유 시 전체 중앙값이 약 0.5 ms(1.28 → 1.83) 늘었다
- 말할 수 없는 것: 실제 데이터센터에서의 지연(같은 호스트 안의 가상 네트워크라 망 지연이 없다), 부하가 있을 때의 지연, 간헐적 지연, 0.55 ms 차이가 측정 잡음과 구분되는지(반복 측정을 하지 않았다)
- 표본이 20회 한 번뿐이고 직접 접속을 먼저 돌렸다. 순서를 바꾸거나 여러 번 반복한 값은 없다

## 미확인
- 순서 효과(LB 경유를 먼저 돌렸을 때의 값), 반복 시 변동폭
- HAProxy 가 더한 시간의 정확한 내역(`option httplog` 로그의 타이밍 값으로 확인할 수 있음)
- LB 경유 초반이 점점 빨라진 원인, tcp 가 LB 경유에서 더 짧게 나온 원인
