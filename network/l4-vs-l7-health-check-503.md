# L4 와 L7 헬스체크 비교: 한 서버가 포트는 열고 503 만 돌려줄 때 (맥, lb01)

## 측정 조건
- 일시: 2026-11-14 14:30 KST 무렵 결과를 받음(실행 시각은 기록하지 않음, 미확인)
- 경로: 맥 → lb01(`192.168.64.7`, HAProxy 2.8.14, `balance roundrobin`, 헬스체크 `inter 2s fall 3 rise 2`) → lab01(`192.168.64.2`), lab02(`192.168.64.3`)
- 같은 서버 두 대를 두 풀에 동시에 둠: L7 풀은 포트 80(`option httpchk GET /health` + `http-check expect status 200`), L4 풀은 포트 81(`mode tcp`, `check` 만 있고 `httpchk` 없음). 설정은 11/14 14:28 배포(`lb_l4_demo=true`)
- 장애 상태: lab02 를 "포트는 열려 있지만 503 만 돌려주는" 상태로 만든 뒤 측정. 학습 자료 1-8 19절 STEP 2 방식으로 보이나(nginx 를 멈추고 같은 80번 포트에 가짜 서버) 사용자가 실행한 명령과 가짜 서버의 응답 내용은 받지 못함(미확인)
- 프로브: `python3 scripts/failover_probe.py <URL> --duration 30`, 간격 0.2초(기본값), 요청 하나씩 순차, `/health`. L7(포트 80) 먼저 한 번, 이어서 L4(포트 81) 한 번. 각 한 번만 실행(반복 안 함)
- 맥과 VM 이 같은 호스트 안의 가상 네트워크

## 읽은 것
- **L7 풀은 실패가 없었다**: 이 측정이 시작될 때 lab02 는 이미 풀에서 빠져 있었다(30초 내내 lab02 응답 0건). HAProxy 가 `/health` 가 503 인 것을 보고 DOWN 으로 판정했다는 해석과 맞다. 다만 상태 페이지나 로그로 DOWN 을 직접 보지는 않았다(미확인)
- **L4 풀은 27초 동안 절반이 실패했다**: 포트에 TCP 연결만 되면 정상으로 보므로 lab02 를 풀에서 빼지 않았고, roundrobin 이 번갈아 보내서 lab02 몫의 요청이 계속 503 을 받았다. 이론상 DOWN 이 되는 6초(`inter 2s × fall 3`)를 훨씬 넘는 27초 동안 비율이 반반으로 유지된 것이 근거다. 상태 페이지에서 `web_l4` 의 lab02 가 UP 이었는지는 보지 않았다(미확인)
- 학습 자료의 예상(L7 약 90% 이상, L4 약 50%)과 비교하면 L4 는 맞았고, L7 은 예상보다 좋은 100% 였다. 이유는 위와 같이 측정 전에 이미 DOWN 이었기 때문이다. 즉 "DOWN 판정 전 약 6초 동안의 일부 실패"는 이 측정에 담기지 않았다
- **L4 의 `lab02 : 5` 는 로드밸런서가 되살린 것이 아니다**: 사용자가 측정 끝 무렵(약 +27초)에 lab02 의 nginx 를 다시 켰고, 그 뒤 lab02 가 정상 응답(200)을 주기 시작한 것이다. L4 풀은 lab02 를 처음부터 빼지 않았으므로 복구가 바로 반영되었다. L7 풀에서는 `rise 2` 때문에 복구 후 연속 2번 성공해야 다시 들어오므로 반영이 늦어질 것(예상, 이번에는 측정하지 않음)
- `+27.0s` 의 `RemoteDisconnected` 1건은 복구 작업(가짜 서버 종료, nginx 시작)과 시각이 겹친다. 실제 원인과 순서는 확인하지 못했다(미확인)
- 스크립트의 `실패 구간 +0.2s ~ +27.0s · 67건` 은 직전 실패와 1초 이내인 실패를 한 구간으로 묶어서 나온 값이다. 그 사이에도 성공이 번갈아 섞여 있었으므로 "27초 중단"이 아니라 "27초 동안 요청의 약 절반 실패"로 읽어야 한다
- 응답 시간은 L7 7 ms, L4 8 ms 로 비슷하다. L4 의 503 은 서버가 즉시 돌려준 에러라 빠르다. 시간만 보면 L4 가 정상처럼 보인다는 점이 "성공률을 함께 봐야 하는 이유"가 된다

## 한계와 미확인
- 측정은 각각 한 번, 30초. 순서를 바꾸거나 반복한 값이 없다
- lab02 를 503 상태로 만든 정확한 시각, 가짜 서버의 명령, 복구 시각(nginx 시작)을 기록하지 못했다
- L7 풀이 lab02 를 DOWN 으로 판정한 시각과 감지 시간은 이 측정으로 알 수 없다(측정 전에 이미 DOWN)
- HAProxy 상태 페이지(`:8008/stats`)의 `L7STS/503` 표시와 `web_l4` 의 UP 표시를 캡처하지 않았다
- 가상 네트워크, 요청 하나씩 순차 호출이라 동시 접속자 영향은 말할 수 없다
- 실험 뒤 정리(`lb_l4_demo` 를 기본값으로 재배포, 81번 방화벽 규칙 제거, lab02 의 가짜 서버 종료와 nginx 상태 확인)의 완료 여부는 확인하지 않았다
