# 3-Tier 설계

> 최초 작성: 2026-11-11 (1-4 3-Tier 설계와 서버 증설)

## 3-Tier 란
서비스를 **웹, 앱, 데이터 세 계층**으로 나눠 각자 다른 서버에 두고, **한 계층은 바로 아래 계층만 부르게** 하는 구조.

```
사용자 → [웹] lab01, lab02 (nginx) → [앱] app01 (uvicorn, first-come-api) → [데이터] db01 (MySQL)
          :80                         :8000                                   :3306
```

## 나누는 이유 네 가지
1. 계층마다 늘리는 단위가 다르다 (웹은 대수를 늘리고, DB는 키운다)
2. 인터넷에 노출된 웹이 뚫려도 DB까지 바로 가지 못한다
3. 한 계층의 장애가 다른 계층을 끌어내리지 않는다
4. 계층마다 따로 배포할 수 있다

## Tier 와 Layer 는 다르다
- Tier: **물리적 배치** (서로 다른 서버)
- Layer: **코드 안의 논리적 구분** (라우터, 서비스, 저장소 함수)
- 한 서버 안에서 코드를 세 겹으로 나눈 것은 3-Layer 이지 3-Tier 가 아니다

## 3-Tier 라고 말할 수 있는 조건은 서버 수가 아니라 경계
- 한 서버에 nginx, 앱, DB 를 다 올려놓고 3-Tier 라고 부르는 경우가 흔하다. 그림은 세 층이지만 경계가 없어서 위 이점이 하나도 생기지 않는다
- 계층 사이에 허용된 통신만 남기고 나머지를 막는 것이 구조를 만든다 → `infra/3tier-access-control.md`
- 순서도 중요: 상자(서버)를 만들고 경계(방화벽)를 친 다음에 서비스를 올린다. 반대로 하면 서비스가 잠깐이라도 경계 없이 노출된다

## 설계 판단
- **lab01, lab02 를 web01, web02 로 이름을 바꾸지 않았다**: 바꾸면 호스트명, 인벤토리, SSH 설정, 지금까지의 문서와 커밋 기록을 전부 손봐야 하고 그 과정에서 실수가 난다. **역할은 호스트명이 아니라 인벤토리 그룹이 정한다.** README 에는 역할로 설명한다
- **여러 계층이 같이 쓰는 변수(`app_port`, `db_port` 등)는 `group_vars/all.yml` 에 한 번만 적는다**: 같은 값이 두 곳에 적히는 순간 언젠가 어긋난다 → `ansible/inventory-groups-vars.md`
